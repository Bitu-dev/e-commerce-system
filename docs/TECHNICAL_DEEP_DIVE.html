1. Distributed Systems Philosophy & Consistency Models

Building an enterprise commerce platform requires reconciling two competing demands: sub-millisecond checkout responsiveness and absolute financial consistency.

Under the CAP Theorem (Consistency, Availability, Partition Tolerance) and the PACELC Theorem, a distributed system facing network partitions must choose between Availability and Consistency. However, applying a single consistency model globally across an entire application is an architectural anti-pattern. Different business aggregates require fundamentally different consistency guarantees:

  • Inventory Allocation (Strong Consistency / CP): Inventory is a scarce physical asset. Under no circumstances can two shoppers be allocated the same physical unit. Inventory updates require ACID transactional serialization and strong consistency.
  • Order Ingestion & Customer Notification (Eventual Consistency / AP): Order placement confirmation and customer push alerts do not require synchronous real-time coordination with the inventory warehouse. They can be accepted asynchronously and finalized via event-driven choreography.

1.1 Why Synchronous Chaining Destroys Availability

Consider an architecture where Order Service synchronously calls Product Service via HTTP REST, which in turn synchronously calls Notification Service. The availability of this chain is the mathematical product of the availabilities of all individual services:

Asystem = Aorder × Aproduct × Anotification × Anetwork2

If each microservice boasts an individual availability of 99.9% (three nines), the combined availability of the synchronous chain degrades to:

Asystem = 0.999 × 0.999 × 0.999 × 0.9992 ≈ 99.5%

This represents an unacceptable downtime increase of 500%. Furthermore, any network blip, garbage collection pause, or database lock wait in notification-service holds connection pool threads open in order-service, rapidly exhausting Tomcat’s thread pool (default 200 worker threads) and bringing down the entire platform.

The Choreography Paradigm Shift
In Aurora Hardware, order-service writes to its local database and immediately publishes an OrderPlacedEvent to RabbitMQ, returning an HTTP 202 Accepted in 14ms. Downstream services consume at their own cadence. If notification-service restarts, RabbitMQ buffers messages in its queue without affecting checkout throughput.

2. Keycloak IAM Deep Dive: OAuth2, PKCE, & JWT Cryptography

2.1 What is Keycloak and Why is it Used?

Keycloak is an enterprise-grade open-source Identity and Access Management (IAM) server stewarded by Red Hat. It provides out-of-the-box OpenID Connect (OIDC) and OAuth 2.0 implementations, user credential storage, password hashing algorithms (Argon2 / PBKDF2), multi-factor authentication (MFA), role-based access control (RBAC), and session management.

In Aurora Hardware, authenticating users inside core microservices (e.g., storing password hashes in order_db) is strictly prohibited. Externalizing IAM to Keycloak ensures:

  • Zero Password Exposure: Backend microservices never handle, store, or salt customer passwords.
  • Single Source of Identity Truth: User profiles and roles (USER, ADMIN) are governed centrally in the mini-commerce realm.
  • Cryptographically Verifiable Tokens: Microservices validate requests offline via asymmetric digital signatures without querying Keycloak on every incoming HTTP call.

2.2 Proof Key for Code Exchange (PKCE with S256 — RFC 7636)

When securing browser-based Single-Page Applications (Next.js), classical OAuth 2.0 Authorization Code Flow required a client_secret. However, SPAs are Public Clients: any code running in the browser can be inspected via Chrome DevTools or JavaScript source maps. Storing a client secret in an SPA is an illusion.

Without a secret, classical authorization code flows are vulnerable to the Authorization Code Interception Attack: a malicious browser extension or network proxy intercepts the authorization code in the redirect URI and exchanges it for a valid access token.

Cryptographic Mathematics of PKCE S256

  1. Code Verifier Generation: The client generates a cryptographically random string V of high entropy using characters [A-Z, a-z, 0-9, -, ., _, ~] with length 43 to 128 characters: 
    code_verifier = "dBjftJeZ4CVP-mB92K27uhbUJU1p1r_wW1gFWFOEjXk"
  2. Code Challenge Computation: The client applies the SHA-256 cryptographic hash function to V and Base64URL-encodes the raw 32-byte digest: 
    code_challenge = Base64URL(SHA-256(code_verifier))
  3. Token Redemption Verification: When exchanging credentials or codes, the client sends V. Keycloak computes Base64URL(SHA-256(V)) and verifies that it exactly equals the registered challenge. Because SHA-256 is a one-way collision-resistant hash function, an attacker who intercepts the challenge cannot deduce V.

2.3 Offline JWT Signature Verification in Spring Boot

A critical architectural innovation in Aurora Hardware is that microservices do not call Keycloak to authenticate incoming requests. Instead, each Spring Boot microservice operates as an OAuth2 Resource Server performing asymmetric offline cryptographic verification: 

# application.yml across all microservices
spring:
  security:
    oauth2:
      resourceserver:
        jwt:
          issuer-uri: http://localhost:8080/realms/mini-commerce
          jwk-set-uri: http://localhost:8080/realms/mini-commerce/protocol/openid-connect/certs

Verification Algorithm:

  • On application startup, Spring Security queries Keycloak's JSON Web Key Set (JWKS) endpoint at /protocol/openid-connect/certs and downloads Keycloak's public RSA certificates, caching them in memory.
  • When an HTTP request arrives with Authorization: Bearer <JWT>, Spring Security mathematically validates the RSA signature on the token header and payload using the cached public key.
  • It verifies that exp (expiration timestamp) is in the future and iss (issuer URI) exactly matches http://localhost:8080/realms/mini-commerce.
  • Latency Impact: The entire authentication check completes in 0.2 milliseconds CPU time with zero network I/O.

2.4 Proactive 45-Second Heartbeat Token Refresh

Access tokens are intentionally short-lived (1,800 seconds / 30 minutes) to minimize exposure windows if intercepted. However, letting an access token expire before taking action causes customer API calls to fail abruptly with HTTP 401 Unauthorized.

In frontend/lib/api-client.ts and components/minicommerce-app.tsx, Aurora Hardware implements a preemptive silent heartbeat:

  • Before executing any API call, ApiClient.ensureValidToken(currentUser) evaluates whether the access token is expired or within 10 seconds of expiry.
  • In parallel, a background timer executes every 45 seconds. If an active session is nearing expiration, it transparently exchanges the refresh token with Keycloak: 
    POST /realms/mini-commerce/protocol/openid-connect/token
grant_type=refresh_token&refresh_token=<RT>&client_id=mini-commerce-web
  • The customer enjoys an uninterrupted browsing session. If the refresh token expires (after 60 minutes of inactivity), the client purges local storage and cleanly transitions to the sign-in screen.

3. Concurrency Control & The Anti-Overselling Algorithm

3.1 The Flash-Sale Race Condition Problem

Consider an e-commerce flash sale for a limited-edition device (e.g., PlayStation 5 Pro) where physical inventory has dwindled to exactly 1 unit.

At 14:00:00.100, Customer A clicks "Submit Order" for 1 unit.
At 14:00:00.102, Customer B clicks "Submit Order" for 1 unit.

In a standard application executing naive SQL queries: 

-- Thread A & Thread B execute in parallel
SELECT stock_quantity FROM products WHERE id = 'prod-ps5-pro'; -- Both read 1
-- Both threads evaluate: 1 >= 1 (True!)
UPDATE products SET stock_quantity = stock_quantity - 1 WHERE id = 'prod-ps5-pro';

Catastrophic Result: Both transactions succeed. Physical warehouse stock is 0, but two customer credit cards were charged and two confirmation emails were sent. This is catastrophic overselling.

3.2 Why Optimistic Locking Fails Under Flash-Sale Contention

A common suggestion is Optimistic Locking via JPA @Version: 

UPDATE products SET stock_quantity = 0, version = 2 WHERE id = 'prod-ps5-pro' AND version = 1;

Under optimistic locking, Thread A commits version 2. When Thread B attempts its update, PostgreSQL detects a version mismatch and Hibernate throws an OptimisticLockingFailureException.

Why this breaks in high-volume production:

  • When 500 customers compete for the last unit simultaneously, 1 transaction succeeds and 499 transactions abort and throw exceptions.
  • Retrying 499 aborted transactions creates an exponential "retry storm", saturating database connection pools, spiking CPU to 100%, and causing cascading timeouts across the entire platform.

3.3 Pessimistic Row Locking (SELECT ... FOR UPDATE)

Aurora Hardware guarantees zero overselling by delegating lock contention directly to PostgreSQL’s internal lock manager using Pessimistic Write Locking: 

// ProductRepository.java
@Lock(LockModeType.PESSIMISTIC_WRITE)
@Query("SELECT p FROM Product p WHERE p.id = :id")
Optional findByIdWithLock(@Param("id") String id);

PostgreSQL Kernel Mechanics

  • When Thread A issues SELECT ... FOR UPDATE, PostgreSQL inspects the tuple header and sets an exclusive XMAX lock flag.
  • When Thread B arrives 2ms later, PostgreSQL's kernel determines that an exclusive tuple write lock is active and suspends Thread B on a lock-wait semaphore.
  • Thread A decrements stock to 0 and executes COMMIT. The commit writes to the Write-Ahead Log (WAL) and releases the row lock.
  • Thread B is awakened. Under PostgreSQL's READ COMMITTED isolation level, Thread B re-evaluates the query condition and reads the newly committed tuple value: stock_quantity = 0.
  • Thread B discovers insufficient inventory, leaves stock untouched, records a failed reservation, and safely publishes an InventoryReservationFailedEvent.
  • Mathematical Invariant: stock_quantity >= 0 is preserved under all concurrency levels.

4. The Transactional Outbox Pattern: Dual-Write Prevention

4.1 The Dual-Write Dilemma in Distributed Systems

When an order is created, the system must perform two discrete state mutations:

  1. Persist the order entity into PostgreSQL (order_db.orders).
  2. Publish an OrderPlacedEvent to RabbitMQ (order.exchange).

In naive implementations, developers write to the database and then call the message broker. If the network drops, RabbitMQ restarts, or the socket times out during the broker call:

  • The database transaction has already committed and cannot be rolled back.
  • The domain event was never received by RabbitMQ.
  • Downstream services never reserve stock or notify the user. The order remains permanently stuck in PENDING status. This is the classic Dual-Write Failure Mode.

4.2 The Transactional Outbox Solution

Aurora Hardware guarantees At-Least-Once event delivery by persisting the event inside the exact same local ACID relational transaction as the business entity:

Implementation in OrderService.java

@Transactional
public Order placeOrder(String customerId, String name, String email, List items) {
    Order order = new Order(customerId, name, email);
    // ... validate and compute totals ...
    order.setStatus(OrderStatus.PENDING);
    Order savedOrder = orderRepository.save(order);

    // Write Outbox record in the exact same ACID transaction
    OutboxEvent outbox = new OutboxEvent(
        savedOrder.getId(),
        "OrderPlaced",
        EventConstants.ROUTING_KEY_ORDER_PLACED,
        objectMapper.writeValueAsString(event)
    );
    outboxEventRepository.save(outbox); // Committed atomically with Order!

    // Attempt immediate AMQP publish
    try {
        amqpTemplate.convertAndSend(EventConstants.EXCHANGE_ORDER, EventConstants.ROUTING_KEY_ORDER_PLACED, event);
        outbox.setStatus("PUBLISHED");
        outbox.setPublishedAt(Instant.now());
        outboxEventRepository.save(outbox);
    } catch (Exception e) {
        log.warn("Immediate publish failed. Outbox background daemon will recover.");
    }
    return savedOrder;
}

Background Polling Daemon (OutboxPublisherService.java)

@Scheduled(fixedDelay = 5000)
@Transactional
public void publishPendingOutboxEvents() {
    List pending = outboxEventRepository.findTop50ByStatusOrderByCreatedAtAsc("PENDING");
    for (OutboxEvent event : pending) {
        try {
            amqpTemplate.convertAndSend(EventConstants.EXCHANGE_ORDER, event.getRoutingKey(), event.getPayload());
            event.setStatus("PUBLISHED");
            event.setPublishedAt(Instant.now());
            outboxEventRepository.save(event);
        } catch (Exception e) {
            event.setRetryCount(event.getRetryCount() + 1);
            outboxEventRepository.save(event);
        }
    }
}

5. Consumer Idempotency & Dead Letter Queue (DLQ) Resilience

5.1 Why Message Brokers Cannot Guarantee Exactly-Once Delivery

In distributed systems, guaranteed delivery across networks can only be achieved via At-Least-Once Delivery.

If a consumer processes an event, deducts inventory in PostgreSQL, and then crashes before sending its AMQP acknowledgment (basicAck), RabbitMQ detects a dropped TCP socket and re-delivers the exact same message to another consumer instance. Consumers must be strictly idempotent: f(f(x)) = f(x).

5.2 Multi-Layered Idempotency Architecture

Service Database Guard Application Code Guard Duplicate Event Outcome
Product Service stock_reservations.order_id UNIQUE stockReservationRepository.existsByOrderId(orderId) Redelivered OrderPlacedEvent is detected immediately; execution exits without secondary stock deduction.
Notification Service notifications.event_id UNIQUE notificationRepository.existsByEventId(eventId) Redelivered lifecycle event is detected; duplicate alert insertion is suppressed.
Order Service Status finite state machine if (order.getStatus() == CONFIRMED) return; Redelivered InventoryReservedEvent produces zero state changes.

5.3 Manual Acknowledgments & Poison Pill Isolation (DLQ)

All consumers configure manual acknowledgment (ackMode = "MANUAL"). A message is only acknowledged after the local database transaction successfully commits: 

try {
    inventoryReservationService.processOrderReservation(event);
    channel.basicAck(deliveryTag, false); // ACK only on commit
} catch (Exception e) {
    // REJECT message WITHOUT requeue -> routes directly to Dead Letter Queue!
    channel.basicNack(deliveryTag, false, false);
}

Why requeue = false is Mandatory:

  • If requeue = true is used on an unparseable JSON message or a database constraint violation, RabbitMQ immediately places the message back at the head of the queue.
  • The consumer reads it again, crashes again, and rejects it again, causing an infinite crash loop that saturates CPU, floods logs, and blocks all subsequent customer orders.
  • With requeue = false and x-dead-letter-exchange: dlx.exchange, RabbitMQ quarantines the poison pill into dead.letter.queue. Healthy orders continue processing unimpeded.

6. End-to-End Scenario Walkthroughs & Code Traces

6.1 Scenario 1: Standard Checkout with Available Stock (Success Path)

  1. Customer Action: Customer Bitaniya places an order for 1 unit of *iPhone 16 Pro Max* (unit price: $49,999.00, available stock: 14).
  2. Client Ingestion: Next.js issues POST :8082/api/orders with Authorization: Bearer <JWT>.
  3. Order Placement:
    • OrderController extracts customer UUID sub claim from JWT.
    • OrderService.placeOrder() creates Order(PENDING) and saves OutboxEvent in order_db in a single ACID transaction.
    • Publishes OrderPlacedEvent to order.exchange (order.placed).
    • Returns HTTP 202 Accepted to browser in 14 milliseconds.
  4. Inventory Allocation:
    • product-service consumes event from inventory.order.placed.queue.
    • InventoryReservationService acquires write lock via findByIdWithLock("prod-iphone-16-pro").
    • Verifies 14 >= 1. Decrements stock to 13.
    • Saves StockReservation(status="RESERVED").
    • Evicts Redis cache (products:all).
    • Publishes InventoryReservedEvent to inventory.exchange (inventory.reserved).
    • Awaits database commit, then issues basicAck.
  5. Order Finalization:
    • order-service consumes InventoryReservedEvent.
    • Transitions order status from PENDING to CONFIRMED.
    • Publishes OrderConfirmedEvent to order.exchange (order.confirmed).
  6. Notification Alerting:
    • notification-service consumes confirmation event and inserts notification record.
  7. Client Polling Completion:
    • Customer browser navigates to /orders and polls GET /api/orders/my.
    • Because the entire choreography round-trip completed in 18ms, the order is already in CONFIRMED status on the very first poll. Visual timeline highlights green; polling halts.

6.2 Scenario 2: Checkout Exceeding Available Stock (Business Rejection Path)

  1. Customer Action: Customer submits an order for 99,999 units of *Apple Watch Ultra 2* (available stock: 8).
  2. Order Placed: Order Service saves order as PENDING and emits OrderPlacedEvent.
  3. Inventory Check:
    • product-service locks row in product_db.
    • Evaluates 8 < 99999. Detects stock shortage.
    • Leaves physical stock untouched at 8 units (zero stock loss).
    • Inserts StockReservation(status="FAILED", reason="Insufficient inventory...").
    • Publishes InventoryReservationFailedEvent to inventory.exchange (inventory.reservation.failed).
  4. Order Rejection:
    • order-service consumes failure event.
    • Transitions status from PENDING to REJECTED.
    • Stores failure reason in orders.rejection_reason.
    • Publishes OrderRejectedEvent to order.exchange.
  5. Client Experience:
    • Client polls GET /api/orders/my and detects REJECTED status.
    • Displays crimson rejection banner with the exact business explanation.

6.3 Scenario 3: Admin Stock Adjustment & Real-Time Cache Eviction

  1. Store administrator logs in as bitaniya.admin and adjusts stock on *PlayStation 5 Pro* from 3 to 8 units.
  2. Next.js client issues PATCH :8081/api/products/prod-ps5-pro/stock with Authorization: Bearer <ADMIN_JWT>.
  3. ProductController validates hasRole('ADMIN').
  4. ProductService.updateStock() locks row, sets stock to 8, commits, and executes @CacheEvict(allEntries=true).
  5. Emits ProductUpdatedEvent (product.updated).
  6. The very next customer query on /shop reads fresh count 8 from PostgreSQL and repopulates Redis with 5-minute TTL.

6.4 Scenario 4: Token Expiration and Silent Preemptive Renewal

  1. Customer has been actively shopping for 29 minutes and 52 seconds (8 seconds remaining on access token).
  2. Customer clicks "View Details" on a product.
  3. ApiClient.ensureValidToken() detects remaining lifespan <= 10 seconds.
  4. Sends refresh_token to Keycloak: POST /protocol/openid-connect/token.
  5. Keycloak returns a new access token valid for another 30 minutes.
  6. Client updates local storage and fires the API request with the fresh token.
  7. Customer experiences seamless zero-friction checkout with zero login interruption.
