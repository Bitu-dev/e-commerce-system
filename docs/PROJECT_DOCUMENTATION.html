2. Executive Summary & Problem Analysis

2.1 Commercial Vision & Business Drivers

Aurora Hardware is a premier luxury e-commerce platform designed for high-concurrency product drops of flagship hardware devices (such as limited-edition smartphones, high-end laptops, noise-canceling audio gear, and gaming consoles). During high-profile flash sales, thousands of shoppers simultaneously compete for single-digit or double-digit quantities of available inventory.

In digital commerce, customer trust is fragile. Overselling inventory—promising an out-of-stock item to a paying customer—creates immense brand damage, chargeback costs, customer support escalation, and legal liability. Conversely, slow checkout response times during peak demand cause elevated shopping cart abandonment rates.

2.2 Core Business Objectives & Key Metrics

  • 100% Inventory Accuracy (Zero Overselling Guarantee): Physical stock must never drop below zero under any degree of concurrency, even when hundreds of requests arrive within the same millisecond.
  • Sub-25ms Order Ingestion Latency: Customer checkout calls must receive an authoritative 202 Accepted confirmation in under 25ms, decoupling the user experience from downstream processing bottlenecks.
  • Zero Dropped Events (Guaranteed Durability): Domain events representing submitted orders must be guaranteed to survive broker network partitions, temporary outages, or power failures.
  • Zero-Trust Identity Governance: Browser clients must never store static shared secrets, and services must cryptographically authenticate every request without centralized database joins.
  • 99.99% Catalog Availability: Storefront browsing must be served with sub-2ms response times via intelligent in-memory caching.

2.3 Analysis of Legacy Architectural Anti-Patterns

Prior to this architecture, early-generation commerce platforms relied on two major architectural patterns that consistently broke under high load:

Anti-Pattern A: Synchronous HTTP Service Chaining

In a synchronous architecture, when a shopper clicks "Place Order", the Order Service initiates a blocking HTTP call to the Product Service to deduct stock, which in turn calls the Notification Service to send a confirmation. This creates a brittle dependency chain:

  • Cascading Latency Amplification: The total checkout time equals the sum of all network round-trips, thread hops, and database transactions. A 500ms slowdown in Notification Service stalls the entire checkout process.
  • Single Point of Complete Failure: If the Notification Service goes offline for maintenance, the Order Service throws a connection timeout, failing the order even though the product was physically in stock.
  • Distributed Rollback Dilemma: If the Product Service deducts stock but the network drops before the Order Service commits, the system enters an inconsistent state requiring complex two-phase commits (2PC) or manual database reconciliation.

Anti-Pattern B: The Shared Monolithic Database

In shared-database designs, multiple services query and mutate the same PostgreSQL database tables. This creates severe architectural degradation:

  • Relational Lock Contention: Long-running analytical reporting or fulfillment queries lock tables required by real-time customer checkouts, causing thread pool exhaustion.
  • Tightly Coupled Schemas: An internal schema change to product catalog tables risks breaking order generation code, preventing autonomous deployments.
  • Violation of Domain Boundaries: Microservices lose domain autonomy and begin executing ad-hoc SQL joins across unrelated business aggregates.
The Aurora Hardware Architectural Paradigm
Aurora Hardware completely eliminates these anti-patterns by enforcing Database-per-Service isolation (three separate PostgreSQL databases) combined with Asynchronous Event Choreography via RabbitMQ topic exchanges. Services communicate exclusively via immutable domain events, achieving true operational decoupling.

3. Architectural Decision Records (ADRs)

The system architecture is governed by six foundational Architectural Decision Records (ADRs) that dictate how concurrency, reliability, persistence, and security are enforced.

ADR-001: Asynchronous Event Choreography with RabbitMQ Topic Exchanges
Context: Cross-service coordination must be resilient, non-blocking, and capable of buffering traffic spikes during flash sales.
Decision: Adopt RabbitMQ topic exchanges (order.exchange, inventory.exchange) and asynchronous consumer listeners. Publishers dispatch events and return immediately without waiting for consumers.
Consequences: System attains extreme horizontal scalability and fault isolation. Downstream service outages do not impact checkout availability. Requires eventual consistency management and customer status polling.
ADR-002: Strict Database-per-Service Relational Isolation
Context: Ensure domain boundaries remain uncompromised and schema evolution is completely decoupled.
Decision: Provision three isolated PostgreSQL databases (product_db, order_db, notification_db) with dedicated database users and credentials. Direct cross-database queries or shared connections are strictly prohibited.
Consequences: Schema changes are 100% localized. To preserve historical integrity, order_items stores immutable snapshots of product names and prices at the time of purchase rather than relying on dynamic database joins.
ADR-003: Pessimistic Row Locking (SELECT ... FOR UPDATE) for Stock Reservations
Context: Extreme write contention on single-digit stock quantities causes race-condition overselling.
Decision: In ProductRepository, stock validation and deduction uses @Lock(LockModeType.PESSIMISTIC_WRITE), issuing SQL SELECT ... FOR UPDATE on the targeted product row.
Consequences: Zero overselling mathematically guaranteed. Avoids optimistic lock retry storms (@Version rollbacks) that crash under high contention. Concurrent transactions queue gracefully at the database engine level.
ADR-004: Transactional Outbox Pattern with Scheduled Polling Recovery
Context: Prevent the dual-write problem where an order is saved in PostgreSQL but fails to publish to RabbitMQ.
Decision: Atomically write an OutboxEvent record into order_db within the exact same ACID database transaction as the order. A background worker (OutboxPublisherService) scans and republishes pending events every 5,000ms if RabbitMQ blips.
Consequences: Guarantees At-Least-Once message delivery. Eliminates brittle Two-Phase Commit (2PC) or XA protocols. Consumers must implement idempotency guards.
ADR-005: Keycloak OAuth2 with PKCE S256 for Public Browser Clients
Context: Secure the Single Page Application without storing static client secrets in client-side code.
Decision: Deploy Keycloak 24 with Proof Key for Code Exchange (PKCE) using SHA-256 (RFC 7636). Spring Boot services validate incoming JWTs offline via cached public JWKS certs.
Consequences: Eliminates secret leakage vulnerabilities. Microservices validate authentication in sub-millisecond offline checks without calling Keycloak per request.
ADR-006: Multi-Tiered Redis Cache-Aside with Event-Driven Eviction
Context: Product catalog reads exceed writes by orders of magnitude; repeated database hits degrade latency.
Decision: Cache catalog responses in Redis 7 with a 5-minute TTL. Evict cache entries immediately upon administrative catalog updates or successful inventory reservations.
Consequences: Catalog read latency drops from ~15ms to <2ms. Storefront reflects fresh inventory counts immediately after orders are finalized.

5. Relational Database Architecture & Complete DDL

In strict compliance with ADR-002, Aurora Hardware provisions three isolated PostgreSQL databases. The complete production DDL for each database is specified below.

5.1 Product & Inventory Database (product_db)

-- ========================================================
-- Database: product_db | Owner: product_user
-- ========================================================

CREATE TABLE products (
    id VARCHAR(64) PRIMARY KEY,
    name VARCHAR(255) NOT NULL,
    category VARCHAR(100),
    description TEXT,
    price NUMERIC(12, 2) NOT NULL CHECK (price >= 0.0),
    stock_quantity INTEGER NOT NULL CHECK (stock_quantity >= 0),
    active BOOLEAN NOT NULL DEFAULT TRUE,
    image VARCHAR(1000),
    badge VARCHAR(100),
    created_at TIMESTAMP WITHOUT TIME ZONE NOT NULL DEFAULT NOW(),
    updated_at TIMESTAMP WITHOUT TIME ZONE NOT NULL DEFAULT NOW()
);

CREATE TABLE stock_reservations (
    id VARCHAR(64) PRIMARY KEY,
    order_id VARCHAR(64) NOT NULL UNIQUE, -- Idempotency Constraint
    status VARCHAR(32) NOT NULL,          -- RESERVED | FAILED
    failure_reason TEXT,
    created_at TIMESTAMP WITHOUT TIME ZONE NOT NULL DEFAULT NOW()
);

CREATE INDEX idx_products_active ON products(active);
CREATE INDEX idx_products_category ON products(category);
CREATE INDEX idx_stock_res_order_id ON stock_reservations(order_id);

5.2 Order Service Database (order_db)

-- ========================================================
-- Database: order_db | Owner: order_user
-- ========================================================

CREATE TABLE orders (
    id VARCHAR(64) PRIMARY KEY,
    customer_id VARCHAR(64) NOT NULL,
    customer_name VARCHAR(255),
    customer_email VARCHAR(255),
    status VARCHAR(32) NOT NULL,          -- PENDING | CONFIRMED | REJECTED
    total_amount NUMERIC(12, 2) NOT NULL CHECK (total_amount >= 0.0),
    rejection_reason TEXT,
    created_at TIMESTAMP WITHOUT TIME ZONE NOT NULL DEFAULT NOW(),
    updated_at TIMESTAMP WITHOUT TIME ZONE NOT NULL DEFAULT NOW()
);

CREATE TABLE order_items (
    id VARCHAR(64) PRIMARY KEY,
    order_id VARCHAR(64) NOT NULL REFERENCES orders(id) ON DELETE CASCADE,
    product_id VARCHAR(64) NOT NULL,
    product_name VARCHAR(255) NOT NULL,   -- Historical Snapshot
    unit_price NUMERIC(12, 2) NOT NULL,   -- Historical Snapshot
    quantity INTEGER NOT NULL CHECK (quantity >= 1),
    subtotal NUMERIC(12, 2) NOT NULL
);

CREATE TABLE outbox_events (
    id VARCHAR(64) PRIMARY KEY,
    aggregate_id VARCHAR(64) NOT NULL,
    event_type VARCHAR(100) NOT NULL,
    routing_key VARCHAR(100) NOT NULL,
    payload TEXT NOT NULL,
    status VARCHAR(32) NOT NULL DEFAULT 'PENDING', -- PENDING | PUBLISHED | FAILED
    retry_count INTEGER NOT NULL DEFAULT 0,
    created_at TIMESTAMP WITHOUT TIME ZONE NOT NULL DEFAULT NOW(),
    published_at TIMESTAMP WITHOUT TIME ZONE
);

CREATE INDEX idx_orders_customer_id ON orders(customer_id);
CREATE INDEX idx_orders_created_at ON orders(created_at DESC);
CREATE INDEX idx_outbox_pending ON outbox_events(status, created_at ASC);

5.3 Notification Database (notification_db)

-- ========================================================
-- Database: notification_db | Owner: notification_user
-- ========================================================

CREATE TABLE notifications (
    id VARCHAR(64) PRIMARY KEY,
    event_id VARCHAR(64) NOT NULL UNIQUE, -- Consumer Idempotency Guard
    customer_id VARCHAR(64) NOT NULL,
    order_id VARCHAR(64) NOT NULL,
    event_type VARCHAR(64) NOT NULL,     -- OrderPlaced | OrderConfirmed | OrderRejected
    message TEXT NOT NULL,
    read BOOLEAN NOT NULL DEFAULT FALSE,
    created_at TIMESTAMP WITHOUT TIME ZONE NOT NULL DEFAULT NOW()
);

CREATE INDEX idx_notif_customer_id ON notifications(customer_id);
CREATE INDEX idx_notif_created_at ON notifications(created_at DESC);
